[2] บทวิเคราะห์ความซับซ้อนของอัลกอริทึม (BIG-O ANALYSIS)
--------------------------------------------------------------------

0. การอ่านและเรียงลำดับข้อมูล (`load_logs.py`) — ใช้ร่วมกันทั้ง Algorithm A และ B
   - การอ่านไฟล์และจัดกลุ่มตาม username ใช้เวลา O(N)
   - การเรียงลำดับแต่ละกลุ่มใช้ `list.sort()` ของ Python ซึ่งใช้อัลกอริทึม Timsort
     ที่เป็น adaptive sort: ถ้าข้อมูลเรียงตามเวลามาอยู่แล้ว (กรณีที่พบได้บ่อยในระบบจริง
     ที่ Log ไหลเข้ามาตามลำดับเวลาเกิดเหตุการณ์) จะใช้เวลาเพียง O(N) โดยไม่ต้องเขียน
     โค้ดตรวจสอบก่อนว่าเรียงแล้วหรือยัง ส่วนกรณีข้อมูลไม่เรียงตามเวลา (แย่ที่สุด) จะใช้
     เวลา O(N log N)
   - รวมขั้นตอนนี้: O(N) ถ้า Log เรียงมาแล้ว / O(N log N) กรณีแย่ที่สุด ไม่ว่าจะนำไปใช้กับ
     Algorithm A หรือ B ก็ตาม (เพราะโหลดผ่านจุดเดียวกัน)

1. Algorithm A (Sliding Window / Two-Pointer)
   - Time Complexity ของตัวอัลกอริทึมเอง (ไม่นับขั้นตอนโหลด/เรียงลำดับซึ่งทำไปแล้วใน
     load_logs.py): O(N)
     * รับข้อมูลที่เรียงลำดับมาแล้วจาก load_logs.py จึงสแกนครั้งเดียวด้วยเทคนิค
       Two-Pointer (left/right) ได้เลยโดยไม่ต้องเรียงลำดับซ้ำ
   - Space Complexity: O(N)
     * ใช้เก็บโครงสร้างข้อมูล dictionary และ list ของเหตุการณ์ login ใน memory

2. Algorithm B (Brute Force)
   - วิธีการ: วนลูปซ้อน (nested loop) ตรง ๆ ทุกคู่ (start, end) ของเหตุการณ์ที่เรียง
     ลำดับแล้ว โดยไม่จัดกลุ่มเป็นชุด (run) ก่อนล่วงหน้าเหมือนที่เคยทำ — ลูปนอกเลือก
     เหตุการณ์ FAILED ทุกตัวเป็นจุดเริ่มต้น (start) ที่เป็นไปได้ ลูปในขยาย end ไปทาง
     ขวาทีละตัวจนกว่าจะเจอ SUCCESS หรือเกินกรอบเวลา 5 นาที แล้วตรวจสอบตรงจุดนั้นว่า
     start เลื่อนไปทางซ้ายอีกไม่ได้แล้ว (is_leftmost) และ end เลื่อนไปทางขวาอีกไม่ได้แล้ว
     (is_rightmost) ก่อนนับว่าเป็นหน้าต่าง (window) ที่ต้องแจ้งเตือนจริง ๆ
   - Time Complexity: O(N^2) ไม่ว่าข้อมูลจะเรียงตามเวลาอยู่แล้วหรือไม่
     * มีการวนลูปซ้อนกันเพื่อตรวจสอบทุกคู่อันดับเริ่มต้นและสิ้นสุดของชุดรายการ FAILED
       ซึ่งเป็นขั้นตอนที่ใช้เวลามากที่สุดและเป็นตัวกำหนด Time Complexity โดยรวม
     * ปัจจุบัน Algorithm B เรียง (sort) ข้อมูลซ้ำอีกครั้งก่อนตรวจจับเสมอ (ไม่ได้รับ
       ประกันว่าผู้เรียกจะส่งข้อมูลที่เรียงมาแล้ว) แต่ด้วย Timsort ที่ adaptive เช่นกัน
       ค่าใช้จ่ายส่วนนี้จะเหลือ O(N) เมื่อข้อมูลเรียงมาแล้ว อย่างไรก็ตาม O(N^2) จากลูป
       ซ้อนยังคงเป็นตัวกำหนด Time Complexity โดยรวมเสมอเมื่อ N มีขนาดใหญ่
     * เมื่อปริมาณ log (N) เพิ่มขึ้น เวลาในการประมวลผลจะพุ่งสูงขึ้นเป็นแบบกำลังสอง
       (ช้ากว่าเดิมเล็กน้อยเมื่อเทียบกับตอนที่เคยกรองด้วยการจัดกลุ่มเป็นชุดก่อน เพราะ
       ตอนนี้ตรวจเงื่อนไข is_leftmost/is_rightmost ในทุกคู่ (start, end) ของเหตุการณ์
       FAILED โดยตรง ไม่ได้กรองด้วยการตัดเป็นชุดล่วงหน้าเหมือนเดิม)
   - Space Complexity: O(N)
     * ใช้พื้นที่หน่วยความจำในการเก็บข้อมูลเท่ากับ Algorithm A


[3] ข้อสรุปเพื่อนำไปเขียนรายงานและสไลด์นำเสนอ (SUMMARY)
--------------------------------------------------------------------
จากผลการทดสอบจริงพบว่า Algorithm A (Sliding Window) ใช้เวลาในการประมวลผล
น้อยกว่าและปรับขนาดได้ดีกว่า Algorithm B (Brute Force) เมื่อจำนวนข้อมูลเพิ่มขึ้น
เนื่องจาก Algorithm A รับข้อมูลที่เรียงลำดับมาแล้วจาก load_logs.py และสแกนเพียง
ครั้งเดียวด้วย Two-Pointer (O(N) เพิ่มเติมจากขั้นตอนโหลดข้อมูล) ในขณะที่ Algorithm B
ยังคงมี Time Complexity เป็น O(N^2) เสมอจากการวนลูปซ้อนตรวจทุกคู่เหตุการณ์ ทำให้
Algorithm A เหมาะสำหรับการรองรับระบบตรวจจับ Log ขนาดใหญ่ในระดับการใช้งานจริง
(Scalability) โดยเฉพาะเมื่อ Log ที่รับเข้ามาเรียงตามเวลาอยู่แล้ว ซึ่งเป็นกรณีที่พบได้บ่อย
ในระบบจริง (เช่น Log ที่ไหลเข้ามาตามลำดับเวลาเกิดเหตุการณ์) และ Timsort ของ Python
จะจัดการกรณีนี้ให้โดยอัตโนมัติโดยไม่ต้องเขียนโค้ดตรวจสอบเพิ่มเอง
